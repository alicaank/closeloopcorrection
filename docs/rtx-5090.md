# Running Spatia and Lyra-2 on our RTX 5090

This describes the actual local inference setup inspected on **2026-10-30**. The machine has one **RTX 5090, 32,607 MiB reported VRAM**, NVIDIA driver **595.99.02**, about **62 GiB usable system RAM**, and 8 GiB swap. These are observations, not minimum hardware specifications. CPU offload makes host RAM and transfer time part of the budget; fitting weights on disk does not mean a rollout fits in GPU memory.

We run one generation job at a time and schedule its geometry/pose-estimation stages sequentially. Separate Python environments avoid mixing the models' CUDA extensions. Nothing in this guide requires stopping an existing experiment or changing the active environments.

## What makes the models fit

| Component | Lyra-2 | Spatia |
|---|---|---|
| Generator | Large diffusion network with DMD LoRA; BF16 host weights | Wan2.2-TI2V-5B + VACE control module + history LoRA; BF16 |
| Weight residency | Load on CPU, then Accelerate sequential CPU offload | Native `enable_vram_management()` and CPU-offloaded T5/VAE/DiT model configurations |
| Text encoder | Precompute exact UMT5 caption embeddings in a separate process | Native staged text-encoder loading/offload |
| Geometry / observer | Offload native DA3 and diffusion stages before external DA3 measurement | MapAnything/render subprocesses plus a separate DA3 worker; DA3 returns to CPU after each measurement |
| Retained history | Native autoregressive history/cache; 96 padding frames are not generated time | 9 history frames per round; saved latent chunks are moved to CPU |
| Output used here | 832×480, 481 total frames | 1248×704, 481 total frames |
| Sampling | `--use_dmd`: **4 fixed denoising steps** | 40 steps, UniPC, CFG 3.5, sigma shift 5 |

The Lyra launcher also passes `--num_sampling_step 35`, but that argument is **ignored by the DMD scheduler**. Do not describe these runs as 35-step Lyra. We did not make these runs fit through 4-bit/8-bit weight quantization, reducing Spatia's official resolution, or training-time activation checkpointing.

This is a selected package inventory, **not a complete environment lock or a recommendation to install a nightly build**. The lightweight Lyra parent launcher delegates model inference to `lyra2`; it does not need the scoring environment's Torch build merely to launch the child. Use each pinned upstream installation guide, then check the native extensions in that model's environment. The [source pins](models.md) and included patches are part of the setup, not optional changes.

Our Lyra launcher points `CUDA_HOME` at the `cuda128` Conda environment and constructs `PATH`, `CPATH` and `LD_LIBRARY_PATH` from the Lyra interpreter's installed Torch/NVIDIA libraries. It sets `NVTE_FLASH_ATTN=0`. Copying only `pip freeze` into a different Torch/CUDA environment does not reproduce those extension and library paths. Spatia's PyTorch3D extension must likewise match its Torch/CUDA build. Do not upgrade the currently running environments to follow this guide.

## Prepare paths and assets

First follow [team setup](setup.md) to materialize a separate workspace and install the native dependencies. On this PC the existing research workspace is `$HOME/Alican` and Conda is `$HOME/miniconda3`; teammates should use their own paths. Run `prepare` only into an **empty new workspace**, never over that existing research workspace.

The following examples operate on a prepared compatibility workspace. Set these to your actual locations:

```bash
export CAMERA_WORKSPACE=/data/camera-work
export CAMERA_CONDA_ROOT=/opt/conda
export CAMERA_BATCH=/data/eval-batch
export CAMERA_RESULTS=/data/camera-results
export CAMERA_SCENE=02267acf
export CAMERA_BASE="$CAMERA_WORKSPACE/analysis/plan_base_restart_20261008"
export CAMERA_CONT="$CAMERA_BASE/continuous_eval_20261029"
export CAMERA_V3="$CAMERA_CONT/scale_20261030/correction_v3_20261030"
```

The environment variables above help write commands; they do not rewrite already-materialized source paths. `config.local.json` must map Conda, weights, cache, child interpreters and ffmpeg correctly **before** `prepare`. Map the observer interpreter even when the launch interpreter is external. See `config.example.json` for the mapping syntax.

Required assets include:

- **Spatia:** the native `model_weights/Wan2.2-TI2V-5B` tree (diffusion shards, Wan2.2 VAE, UMT5 encoder/tokenizer), `control_weight_8500.safetensors` and `lora_weights_10000.safetensors` at the adapter's configured `baselines/models/spatia` location; MapAnything and rendering dependencies/caches; external DA3 weights.
- **Lyra-2:** `Lyra-2/checkpoints/model`, `checkpoints/vae`, `checkpoints/text_encoder/negative_prompt.pt`, the UMT5 encoder assets for cache preparation, and `checkpoints/lora/dmd_distillation.safetensors`; native DA3/MoGe assets and the external DA3 observer cache. The launcher uses the DA3 snapshot recorded in its source and the asset inventory.
- **Both:** a registered image/depth/intrinsics/trajectory batch with enough frames, and the mapped ffmpeg executable. The weights and text embeddings are not in this Git repository.

Keep native model directories/filenames expected by the pinned code, or supply explicit path mappings. A generator checkpoint by itself is not sufficient for a correction rollout.

## Lyra-2: precompute captions, then generate

The text encoder cache is essential on this machine. The previous in-process UMT5 load alongside the offloaded diffusion model pushed host RSS to approximately 58 GiB and runs were killed by the OS. Sequential GPU offload alone did not fix that. `GV_LYRA_BF16=1` also casts the diffusion network to its configured inference dtype on CPU, avoiding an FP32 host copy persisting through the DMD setup.

When the GPU is available, cache **every exact caption string** used by the batch before launching Lyra:

```bash
# The wrapper uses the relocated Lyra/CUDA paths and runs UMT5 alone.
# Use a fresh cache for a changed batch; do not overwrite one used by a running job.
if [ ! -f "$CAMERA_CONT/lyra_t5.pt" ]; then
  CUDA_VISIBLE_DEVICES=0 NVTE_FLASH_ATTN=0 \
    bash "$CAMERA_BASE/lyra2_plugins/run_t5_captions.sh" \
    "$CAMERA_BATCH" "$CAMERA_CONT/lyra_t5.pt"
fi
```

By default the launcher sets `GV_T5_CACHE` to that file. For multiple datasets, use `run --t5-cache` / `run-batch --t5-cache` or set `CAMERA_LYRA_T5_CACHE` for direct launchers; see [the dataset guide](datasets.md). The cache reader fails when a requested caption is absent; reuse is valid only when all current captions are present. If the file is missing, the legacy plugin can fall back to loading UMT5 in-process, recreating the host-memory problem. Check the file before generation.

Start with an **81-total-frame** scale/timeline pilot, then run the matched long arms after reviewing its geometry:

```bash
CUDA_VISIBLE_DEVICES=0 "$CAMERA_LAUNCH_PY" "$CAMERA_V3/lyra_v3.py" \
  --batch "$CAMERA_BATCH" --scene "$CAMERA_SCENE" \
  --out "$CAMERA_RESULTS/lyra-${CAMERA_SCENE}-pilot81" \
  --arm baseline --frames 81 --observer-quality enforce

# A new output directory is required for each arm/run.
for arm in baseline sham correction; do
  CUDA_VISIBLE_DEVICES=0 "$CAMERA_LAUNCH_PY" "$CAMERA_V3/lyra_v3.py" \
    --batch "$CAMERA_BATCH" --scene "$CAMERA_SCENE" \
    --out "$CAMERA_RESULTS/lyra-${CAMERA_SCENE}-${arm}-481" \
    --arm "$arm" --frames 481 --observer-quality enforce || break
done
```

These are the bundled **v3 guarded** entrypoints; their GPU qualification is still pending. Completed local runs cited below used `continuous_eval_20261029/lyra_run.py`. The memory strategy is retained in the v3 snapshot, but the new observer gate must be qualified separately.

The wrapper supplies `--offload --sequential_cpu_offload --offload_when_prompt --offload_da3_diffusion --use_dmd`, 480×832 resolution, seed 7 and the native checkpoint paths. The upstream patch loads the network on CPU, avoids incompatible checkpoint-wrapped parameter names when attaching Accelerate hooks, and prevents a later restore call from moving the whole sequentially offloaded network back onto the GPU. Merely adding `--offload` to an unpatched upstream checkout is not the same recipe.

## Spatia: staged loading and point-cloud visibility

Spatia's native `build_pipe()` configures BF16 and CPU-offloaded text encoder, VAE and diffusion weights, then calls `enable_vram_management()`. The harness processes MapAnything/rendering and generation in rounds, keeps completed latent chunks on CPU, and uses a DA3 worker that loads on CPU and moves onto the GPU only during a measurement. We use 121 frames for the first round, 81 for later rounds and 9 overlapping history frames, with 40 denoising steps. The official render size remains 1248×704.

The difficult peak is not always diffusion: point-cloud visibility can grow with accumulated geometry and candidate views. Our v3 wrapper batches **one camera view at a time while preserving the original point partition**. Reducing the point partition can change occlusion decisions and is not an equivalent memory optimization. This view-batching fix still needs CUDA mask/matching parity and peak-memory validation.

Use a **193-total-frame** two-round pilot to exercise continuation and visibility. First isolate the memory change; then repeat with the observer quality gate enabled, using separate directories:

```bash
# Memory-only pilot. Run only after the separate CUDA visibility-parity check.
env -u LD_LIBRARY_PATH CUDA_VISIBLE_DEVICES=0 \
  "$CAMERA_SPATIA_PY" "$CAMERA_V3/spatia_v3.py" \
  --batch "$CAMERA_BATCH" --scene "$CAMERA_SCENE" \
  --out "$CAMERA_RESULTS/spatia-${CAMERA_SCENE}-memory193" \
  --arms baseline,sham,replan_commanded --seed 7 \
  --num_frames 193 --first_round_frames 121 --round_frames 81 --hist_frames 9 \
  --meas_stride 12 --min_free_gib 18 \
  --visibility-views-per-batch 1 --observer-quality off

# Same memory fix, add the quality gate as the only changed factor.
env -u LD_LIBRARY_PATH CUDA_VISIBLE_DEVICES=0 \
  "$CAMERA_SPATIA_PY" "$CAMERA_V3/spatia_v3.py" \
  --batch "$CAMERA_BATCH" --scene "$CAMERA_SCENE" \
  --out "$CAMERA_RESULTS/spatia-${CAMERA_SCENE}-quality193" \
  --arms baseline,sham,replan_commanded --seed 7 \
  --num_frames 193 --first_round_frames 121 --round_frames 81 --hist_frames 9 \
  --meas_stride 12 --min_free_gib 18 \
  --visibility-views-per-batch 1 --observer-quality enforce
```

The separate CUDA visibility-parity check belongs to the existing local v3 validation queue; it has not been reproduced by the portable package's CPU suite. Do not label these settings GPU-qualified merely because the commands parse. After those gates pass, repeat the selected protocol with `--num_frames 481` and a fresh output directory. The v3 wrapper stops after an arm exception; retry in a fresh process rather than continuing after a CUDA OOM.

The local historical queue uses `--prune_work` to remove that run's intermediate point clouds after outputs are written. The examples above retain intermediates for inspection; plan disk space accordingly. Do not delete model checkpoints or shared assets to make a pilot fit.

## Operational checks and common failures

Before launching, inspect the existing queue, `nvidia-smi`, `free -h` and `df -h`. T5 precomputation also uses the GPU; schedule it, generation and scoring sequentially. Do not start a second model just because one sampled GPU-memory reading looks low. CPU offload still needs available host RAM, and swap is not a substitute for it.

- **OS kills the process / exit 137:** inspect host-memory pressure; verify cached captions and the BF16 CPU-loading path. This can happen without a CUDA OOM.
- **CUDA OOM during Spatia visibility/reference selection:** preserve the failed logs and qualify view batching. Lowering denoising steps alone does not shrink the offending visibility tensor.
- **`_checkpoint_wrapped_module` / offload weight-map `KeyError`:** verify the pinned Lyra offload patch and that checkpoint wrapping was deferred before attaching Accelerate hooks.
- **Missing kernel, extension or shared-library error:** check the exact model interpreter, Torch/CUDA extension build and library paths. A driver update alone does not repair a mismatched Python extension.
- **Large camera jumps despite fitting memory:** check registered anchor depth, crop/intrinsics, native scale, output/latent frame IDs and continuation alignment. Memory optimizations do not validate geometry. Do not force calibration to produce an execution ratio of 1.05.

Keep baseline/sham/correction seed, native sampling settings, frame counts and calibrated geometry matched. Any lower resolution, smaller history or altered sampler is a separate configuration and must be reported as such.
